- 『진리표에서 GPU까지』라는 본제와 본문 1장이 실제 진리표에서 출발하는 구성

- 1장: AND·NAND·NAND를 이용한 AND 구현의 진리표가 모두 맞다.

## 원고 집필 전에 반드시 해결할 항목

### 1. 계산 요구량과 기계 자원의 구분

- 위치 또는 검토 대상: `planning/chapter-map.md` 서장의 비용 지도와 8·9·12장
- 문제의 내용: 연산 횟수 같은 계산의 요구량과 연산기 수 같은 기계 자원을 한 장부에서 직접 대응시키고 있다.
- 중요도: 높음
- 범주: 2 설명상의 문제
- 문제가 되는 이유: 같은 연산량을 더 많은 연산기로 처리하는 경우를 일관되게 기록하기 어렵다.
- 구체적인 수정안: 비용 지도를 `계산이 요구하는 양`과 `기계가 제공하는 자원`의 두 열로 나누고, 비용은 둘의 관계에서 생긴다고 설명한다.
- 수정하지 않을 경우의 위험: 네 비용 장부의 항목이 장마다 임의로 늘어나 책의 핵심 비교 틀이 약해진다.

### 2. 행렬 연산 장치를 systolic 계열로 일반화할 위험

- 위치 또는 검토 대상: `planning/chapter-map.md` 19장
- 문제의 내용: systolic dataflow의 일반 원리 바로 뒤에 Tensor Core·MFMA·XMX·TPU MXU를 나열하면 모두 같은 내부 데이터 흐름을 쓴다는 인상을 줄 수 있다.
- 중요도: 높음
- 범주: 1 기술적 오류
- 문제가 되는 이유: TPU MXU의 systolic 설명과 달리 다른 장치의 내부 데이터 흐름은 공개 자료만으로 같은 수준까지 특정하기 어렵다.
- 구체적인 수정안: `반복 MAC을 전용 데이터 경로에 고정하는 일반 원리`와 `systolic 데이터 흐름이라는 특정 계열`을 분리한다. 사례 표에는 공개 자료로 확인된 연산 종류·형식·모양만 쓴다.
- 수정하지 않을 경우의 위험: 서로 다른 제품 구조를 동일시했다는 핵심 기술 오류가 된다.

### 6. 17장 부분합 저장 위치 명시

- 문제의 내용: A·B 입력 타일의 가까운 저장공간은 명시했지만, C 결과 타일의 부분합이 어디에 머무는지는 밝히지 않았다.
- 중요도: 중간
- 범주: 1 기술적 오류
- 문제가 되는 이유: 부분합을 밖으로 내보내면 결과 쓰기 16회라는 수치가 성립하지 않는다. 48회 대안도 두 결과 타일의 부분합 보존을 전제한다.

- 수정하지 않을 경우의 위험: 독자가 같은 수치를 재현할 수 없다.

- 중요도: 중간
- 범주: 3 구조·시장성·차별성
- 문제가 되는 이유: 표지가 수학 중심의 비용 서사 또는 AI 가속기까지의 범위를 정확히 알리지 못할 수 있다.

## 독립 편집 판단

검토 결과의 큰 방향에는 동의한다. 특히 발견 1·2·4·5·10은 원고의 정확성과 책의 고유한 비교 틀에 직접 영향을 주므로 우선 반영할 가치가 높다. 발견 3은 자료 우선순위 원칙상 타당하다. 발견 7은 부제가 애초 미확정이므로 즉시 확정할 문제가 아니라 후보군과 문서 상태를 동기화할 문제다.

발견 6은 부분적으로만 수용한다. C 부분합의 저장 위치를 명시해야 한다는 지적은 맞지만, 48회 대안에서 C 결과 타일 두 개를 동시에 유지해야 한다는 주장은 틀리다. A 타일 두 개를 남겨 둔 채 C00을 완성해 쓰고 C01을 차례로 완성하면 C 결과 타일 하나의 부분합 네 개만 보존해도 입력 읽기 48회가 성립한다. 수정본에는 입력 저장공간과 결과 누산 공간을 분리하고 이 실행 순서를 명시한다.

발견 8의 `행렬 원소` 삭제와 발견 12는 단순하고 명백한 정리 대상이다. 발견 9는 취지는 좋지만 16장 전에 AI 층의 곱셈-누산 수를 세는 예제는 행렬을 조기 도입하는 우회로가 될 수 있으므로 그대로 수용하지 않는다. 11장에서는 그래픽과 AI를 같은 계산으로 만들기보다 `독립된 많은 항목에 비슷한 수치 규칙을 반복한다`는 공통점을 작은 작업표로 비교하는 정도가 더 적절하다.

그래픽에서 AI로 이어지는 역사 서사는 유지할 가치가 있다. 다만 이를 `인류사적 우연`이라는 한 문장으로 결론내리기보다, 그래픽에서 형성된 데이터 병렬 처리 기반과 프로그래밍 가능성이 딥러닝의 대량 수치 계산과 접점을 얻었고 GPGPU 도구·프로그래밍 생태계가 실제 전환을 가능하게 했다고 설명해야 한다.
