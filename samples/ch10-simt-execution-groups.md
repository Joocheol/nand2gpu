# 샘플 2 — 10장: 같은 식 안에서 서로 다른 길을 고를 때

상태: 설명 방식 검증용 초안

## 독립된 일처럼 보이지만 함께 움직인다

사진의 밝기를 조정한다고 해보자. 사진에는 수많은 픽셀이 있고, 각 픽셀의 밝기에 10을 더한다고 하자. 픽셀마다 입력값은 다르지만 적용할 계산 규칙은 같다.

이전 장에서 본 **SIMD(Single Instruction, Multiple Data, 단일 명령 다중 데이터)**는 하나의 명령으로 여러 데이터 요소를 계산한다. 넓은 상자 하나에 여러 숫자를 넣고 한꺼번에 더하는 모습으로 생각할 수 있다.

GPU 프로그램은 같은 병렬성을 다른 방식으로 드러낸다. 프로그래머에게는 픽셀마다 작은 작업자 하나, 즉 **스레드(thread)** 하나가 있는 것처럼 보이게 한다. 각 스레드는 자기 픽셀 번호와 자기 레지스터 값을 가진다.

여기서 GPU는 같은 종류의 계산을 아주 많은 데이터에 적용하는 일을 높은 처리량으로 맡도록 발전해 온 계산 장치라고만 알아두자. 그런 일이 그래픽에서 왜 필요했고 나중에 AI와 어떻게 만났는지는 다음 장에서 역사와 함께 다룬다.

그렇다고 실제 하드웨어가 스레드마다 완전한 명령 제어 장치를 하나씩 따로 주는 것은 아니다. 그렇게 하면 제어회로와 명령어 읽기 비용이 지나치게 커진다. GPU는 여러 스레드를 한 묶음으로 만들고 같은 명령을 함께 내보낸다. 이를 **SIMT(Single Instruction, Multiple Threads, 단일 명령 다중 스레드)** 실행 모델이라고 한다.

여기에는 두 관점이 겹쳐 있다.

- 프로그램 관점: 각 스레드는 자기 상태와 작업 대상을 가진다.
- 하드웨어 관점: 여러 스레드를 묶어 같은 명령을 실행 레인에 공급한다.

SIMT와 SIMD는 완전히 무관한 구조가 아니다. 둘 다 제어를 공유해 여러 데이터 계산의 비용을 낮춘다. 다만 SIMD는 넓은 데이터 묶음을 명시적으로 다루는 관점이고, SIMT는 독립된 스레드들을 같은 명령 아래 묶는 관점을 제공한다.

이 차이는 하드웨어의 실행 폭이 달라질 때와 일부 계산이 데이터를 기다릴 때 중요해진다. 프로그램은 픽셀이나 격자의 각 칸마다 독립된 일을 표현하고, 하드웨어는 실제 실행 폭에 맞춰 스레드를 묶는다. 한 묶음이 메모리를 기다리면 준비된 다른 묶음의 계산을 꺼낼 수도 있다. 이 장에서는 묶음 안에서 길이 갈라지는 비용을 먼저 보고, 묶음 사이를 바꾸는 상세한 방법은 뒤에서 다룬다.

## 네 스레드로 줄여 본 실행 묶음

실제 제품보다 작은 네 스레드 묶음을 가정하자. 네 픽셀의 밝기는 다음과 같다.

| 스레드 | 원래 밝기 | 10을 더한 값 |
|---:|---:|---:|
| 0 | 30 | 40 |
| 1 | 80 | 90 |
| 2 | 90 | 100 |
| 3 | 200 | 210 |

하드웨어는 네 스레드에 “10을 더하라”는 명령을 한 번 내보낸다. 네 실행 레인은 서로 다른 입력을 사용하므로 결과도 40, 90, 100, 210으로 다르다. 명령은 공유하지만 데이터와 결과는 스레드마다 다르다.

이 구조에서 얻는 것은 처리량이다. 같은 명령을 네 번 읽고 해석하는 대신 한 번의 제어로 네 계산을 진행할 수 있다. 대가는 같은 종류의 일을 충분히 모아야 실행 레인을 낭비하지 않는다는 점이다.

## 서로 다른 길을 고르면 생기는 일

이번에는 밝기가 100 이상이면 절반으로 줄이고, 100보다 작으면 20을 더한다고 하자. 하나의 조각별 함수다.

| 스레드 | 입력 | 조건: 100 이상? | 실행할 일 | 결과 |
|---:|---:|:---:|---|---:|
| 0 | 30 | 아니요 | 20을 더한다 | 50 |
| 1 | 80 | 아니요 | 20을 더한다 | 100 |
| 2 | 90 | 아니요 | 20을 더한다 | 110 |
| 3 | 200 | 예 | 2로 나눈다 | 100 |

스레드 0·1·2는 “20을 더한다”는 길을 고르고, 스레드 3은 “2로 나눈다”는 길을 고른다. 한 묶음 안에서 실행 경로가 갈라지는 현상을 **분기 발산(branch divergence)**이라고 한다.

단순화한 하드웨어가 먼저 나눗셈 경로를 실행한다고 가정하자. 이때 스레드 3만 활성화하고 나머지 세 레인은 꺼 둔다. 그다음 덧셈 경로를 처리할 때는 스레드 0·1·2만 활성화하고 스레드 3의 레인을 꺼 둔다. 결과는 모두 정확하지만 두 경로를 따로 통과하는 동안 일부 실행 레인이 쉰다.

효율 감소를 작은 숫자로 세어 보자. 여기서 3단계와 2단계는 특정 GPU에서 `2로 나누기`와 `20 더하기`가 실제로 걸리는 시간을 주장하는 숫자가 아니다. 두 경로의 길이가 다른 상황에서 분기 발산만 분리해 보기 위해 정한 **교육용 명령 단계**다. 실제로 `x/2`가 어떻게 구현되는지는 수의 형식과 명령어에 따라 다르다.

- 나눗셈 경로가 3개의 명령 단계라고 가정한다.
- 덧셈 경로가 2개의 명령 단계라고 가정한다.
- 발산한 구간 전체는 3 + 2 = 5단계를 차례로 실행한다.
- 네 레인이 다 일했다면 최대 작업량은 5단계 × 4레인 = 20 레인-단계다.
- 실제 유효 작업량은 나눗셈 경로의 3×1과 덧셈 경로의 2×3을 더한 9 레인-단계다.

이 단순한 구간의 활성 레인 비율은 9 ÷ 20 = 0.45, 즉 45%다. 긴 나눗셈 경로를 고른 스레드가 하나뿐이라 그 세 단계에서 세 레인이 함께 쉰 결과다. 이것은 프로그램의 정답이 45%만 맞는다는 뜻이 아니다. 같은 정답을 얻는 동안 실행 자원이 충분히 활용되지 않았다는 뜻이다.

실제 GPU에서는 명령마다 걸리는 시간, 스케줄러, 독립 스레드 실행, 두 경로를 모두 계산한 뒤 필요한 값만 남기는 변환 등이 더 복잡하게 작용한다. 위 계산은 분기 발산의 비용이 왜 생기는지 보여주기 위한 모형이지 특정 제품의 실제 실행 시간을 예측하는 공식이 아니다.

## warp와 wavefront는 사례 이름이다

스레드 실행 묶음에는 회사별 이름이 있다.

- NVIDIA는 이 묶음을 **warp(워프)**라고 부른다. 현재 CUDA 실행 모델에서 한 warp는 32개 스레드로 설명된다.
- AMD는 대응되는 실행 묶음을 **wavefront(웨이브프런트)**라고 부른다. 폭은 아키텍처와 실행 모드에 따라 32 또는 64가 될 수 있다.

따라서 “GPU의 실행 묶음은 언제나 32개”라고 일반화하면 틀린다. 반대로 warp와 wavefront를 이름만 다른 완전히 동일한 부품이라고 말해도 정확하지 않다. 둘은 제어를 공유하는 스레드 묶음이라는 일반 원리를 보여주는 서로 다른 회사의 구현 사례다.

### 선택 보충: 스레드가 언제나 한 치의 차이도 없이 움직이는가

NVIDIA의 일부 현대 아키텍처에는 **독립 스레드 스케줄링(Independent Thread Scheduling)**도 도입되어 스레드별 실행 상태를 더 유연하게 다룬다. 그렇더라도 성능을 이해할 때 warp 단위의 명령 실행과 분기 발산이 사라진 것은 아니다. “항상 한 치의 차이도 없이 함께 움직인다”와 “각 스레드가 아무 관계 없이 완전히 따로 실행된다”는 설명 모두 피해야 한다. 이 용어는 본문의 필수 학습 항목이 아니라 회사별 구현 차이를 정확하게 제한하기 위한 보충이다.

## 공유해서 얻은 것, 공유해서 생긴 제약

SIMT는 각 스레드가 독립된 작업자인 것처럼 문제를 표현하게 하면서, 하드웨어에서는 명령과 제어 비용을 여러 실행 레인이 나눠 부담하게 한다. 이것이 **공유**의 이익이다.

그러나 공유한 제어 아래에서는 같은 시점에 비슷한 일을 하는 스레드가 많을수록 유리하다. 서로 다른 분기로 흩어지거나 일부 스레드만 남으면 공유의 이익이 줄어든다. 서로 다른 주소에서 데이터를 가져오는 비용은 뒤의 메모리 장에서 따로 다룬다.

## 이번 장의 선택과 비용

| 구분 | 기록 |
|---|---|
| 보존한 기능·정확한 결과 | 네 입력에 정의한 조각별 함수와 결과 `50, 100, 110, 100` |
| 계산이 요구하는 양 | 네 독립 계산, 두 갈래의 교육용 명령 단계 3개와 2개, 유효 작업 9 레인-단계 |
| 기계가 제공할 자원 | 제어를 공유하는 실행 레인 4개와 경로별 활성 마스크 |
| 설계 대가 | 제어 비용을 나누는 대신 발산 구간에서 일부 레인이 쉼. 교육 모형의 활성 레인 비율은 45% |
| 아직 해결되지 않은 제약 | 수백만 개의 계산을 더 적은 실행 자원에 어떻게 배치하고 데이터 대기 시간을 어떻게 감추는가 |
